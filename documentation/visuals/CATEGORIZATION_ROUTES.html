Categorization — Every Route a Transaction Takes

A first-claim-wins cascade: a PENDING bank transaction is offered to each stage in order. A claim stage either claims it (→ a journal entry) or passes it down. The one transform stage (enrichment) claims nothing — it just resolves who the counterparty is, which several later routes depend on.

Human / secondary routes (after the cascade)

  • 7b NEEDS_REVIEW → resolve_needs_review → JE + MATCHED.
  • 8 PENDING → manual_categorize → JE + MATCHED.
  • Any MATCHED / AWAITING → approve → the DRAFT JE flips to POSTED, txn → RECONCILED (the ledger gate — only now is it in the reports); reject → JE voided, txn → PENDING.
  • Retroactive AP: an invoice approved later can re-open a previously-categorized payment and knock it off.

Reading it for the phase review

  • Every JE-producing route (1–7a) creates a DRAFT JE; reconcile/approve posts it. "Lands as a JE" = claimed by routes 1–7a.
  • Enrichment is the only non-claiming stage — it gates routes 3a/3b, 6, and counterparty-type rules inside 5. Routes keyed on description/amount don't need it.
  • Strict first-claim-wins — the open question for the review: can two stages plausibly both claim the same txn (precedence ambiguity)? e.g. a salary payment that also matches an expense rule.
  • RAG's home is Route 7 (4D AI) — it only ever sees what routes 1–6 couldn't claim.
